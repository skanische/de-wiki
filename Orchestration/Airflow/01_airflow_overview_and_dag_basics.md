# Airflow Overview and DAG Basics

## 1. Кратко

- Airflow — это оркестратор: он описывает пайплайны как DAG, запускает их по расписанию или вручную, координирует выполнение задач и помогает контролировать результат.
- Чаще всего Airflow применяется для работы с данными: ingestion, transform/load, batch-пайплайны, регулярные проверки, запуск Spark/dbt/SQL jobs, уведомления.
- Airflow не является движком обработки данных. Он не должен сам обрабатывать большие объёмы данных внутри worker-процесса.
- DAG — это представление пайплайна в виде ацикличного графа: вершины — задачи, рёбра — зависимости между ними.
- Scheduler решает, какие задачи готовы к выполнению, и ставит их в очередь.
- Worker выполняет конкретные task instances, которые scheduler поставил в очередь.
  - _Замечание:_ Для вводной mental model worker — исполнитель task instance. Конкретный способ запуска зависит от выбранного executor.
- Operator описывает единицу работы. Когда operator используется внутри DAG, он становится конкретной task.
- UI нужен для визуализации структуры DAG, истории запусков, состояния task instances, просмотра логов и диагностики ошибок.
- Если упала конкретная task, её можно перезапустить после отладки, не перезапуская весь DAG целиком.
- Чтобы rerun был безопасным, task должна быть атомарной и идемпотентной.
- Airflow плохо подходит для streaming pipelines и сильно динамических pipeline, где структура task радикально меняется между запусками.


## 2. Зачем это нужно и где используется

Airflow нужен там, где есть не одна команда или один скрипт, а последовательность связанных шагов.

Например:

- скачать данные из API;
- сохранить raw-слой;
- проверить, что данные не пустые и схема корректная;
- преобразовать данные;
- записать витрину;
- отправить уведомление.

Такой процесс можно написать одним Python-скриптом, но у этого подхода есть проблемы:

- если скрипт упал посередине, сложнее понять, на каком именно шаге проблема;
- после исправления ошибки часто приходится перезапускать всё целиком;
- нет нормальной истории выполнения каждого шага;
- неудобно смотреть длительность отдельных частей;
- сложнее управлять retry, логами и алертами;
- нельзя нормально распараллелить независимые части процесса.

Airflow решает это тем, что раскладывает процесс на отдельные task, связывает их зависимостями и контролирует выполнение.

Пример DE-сценария:

```
download_data >> check_raw_data >> save_to_storage >> email_end
```

Где:

- `download_data` скачивает raw-данные;
- `check_raw_data` проверяет файл;
- `save_to_storage` запускает обработку и запись витрины;
- `email_end` отправляет уведомление.

Главная мысль:

> Airflow не заменяет специализированные системы обработки данных.
> Он запускает и координирует Python-код, Spark jobs, SQL-запросы, API-вызовы и другие внешние операции.


## 3. Базовая mental model

Airflow — это оркестратор workflow.

Он:

1. Читает Python-файлы с описанием DAG.
2. Извлекает из них структуру DAG: task, dependencies, schedule и metadata.
3. Определяет, когда нужно создать запуск DAG.
4. Проверяет, какие task готовы к выполнению.
5. Ставит готовые task instances в очередь.
6. Workers забирают task instances из очереди и выполняют их.
7. Состояния task и DAG runs сохраняются в metastore.
8. UI показывает структуру, историю запусков, статусы и логи.

Упрощённая схема:

```
DAG file
  ↓
Scheduler parses DAG
  ↓
Scheduler decides which task instances are ready
  ↓
Execution queue
  ↓
Workers execute task instances
  ↓
Metastore stores states/results
  ↓
UI shows DAG, runs, task states and logs
```

Основные сущности:

| Сущность | Что означает |
|---|---|
| DAG | Ацикличный граф workflow |
| Task | Конкретная вершина DAG |
| Operator | Тип/реализация единицы работы |
| Task Instance | Конкретное выполнение task в рамках конкретного DAG Run |
| DAG Run | Конкретный запуск DAG |
| Scheduler | Компонент, который планирует выполнение |
| Worker | Компонент, который выполняет task instances |
| Webserver / UI | Интерфейс для просмотра DAG, запусков, статусов и логов |
| Metastore | База metadata и состояний Airflow |
| Execution queue | Очередь task instances, готовых к выполнению |

Важно не путать:

- DAG — это не обычный цикл и не последовательный скрипт.
- DAG может быть не только цепочкой, но и ветвящимся графом.
- Worker не запускает весь DAG-файл целиком, а выполняет конкретные task instances.
- Airflow не должен выполнять тяжёлую обработку данных сам; он должен запускать подходящий инструмент.


## 4. Как это работает внутри

### DAG как граф

DAG расшифровывается как Directed Acyclic Graph.

Это значит:

- Directed — зависимости имеют направление;
- Acyclic — в графе нет циклов;
- Graph — есть вершины и рёбра.

Пример корректного DAG:

```
A >> B >> C
```

Пример некорректной структуры:

```
A >> B
B >> C
C >> A
```

Это уже невалидный DAG, потому что есть цикл.

При цикле Airflow не может построить корректный порядок выполнения задач. Возникает circular dependency: задача A ждёт B, B ждёт C, C ждёт A. В такой структуре невозможно определить нормальную стартовую точку и порядок выполнения.

Правильная формулировка:

DAG — это не просто “задачи идут одна за другой”. DAG — это граф зависимостей, по которому Airflow может вывести допустимый порядок выполнения.


### Как Airflow выбирает task для выполнения

В упрощённой логике:

1. Airflow парсит DAG-файлы scheduler определяет готовые к выполнению task instances.)
2. Scheduler определяет готовые к выполнению task instances.
3. Для каждой task проверяет upstream dependencies.
4. Если зависимости выполнены и правила запуска позволяют, task instance может быть поставлена в очередь.
5. Worker забирает task instance и выполняет её.
6. Результат выполнения сохраняется в metastore.

Для простого DAG:

```
extract >> validate >> load >> notify
```

По умолчанию:

- `validate` начнётся только после успешного `extract`;
- `load` начнётся только после успешного `validate`;
- `notify` начнётся только после успешного `load`.

Если `validate` упадёт, `load` и `notify` по умолчанию не запустятся.


### Основные компоненты Airflow

| Компонент | Роль |
|---|---|
| Scheduler | Парсит DAG-файлы, проверяет расписание и зависимости, решает, какие task instances готовы к выполнению |
| Worker | Выполняет конкретные task instances |
| Webserver / UI | Показывает DAG, структуру, историю запусков, статусы и логи |
| Metastore | Хранит состояния DAG Run, Task Instance и другую metadata |
| Execution queue | Очередь task instances, которые готовы к выполнению |

Важное уточнение:

Worker не запускает “скрипт DAG целиком”. DAG-файл описывает структуру workflow. Worker выполняет конкретную task instance.


### Task vs Operator vs Task Instance

Пример:

```
download_data = BashOperator(
    task_id="download_data",
    bash_command="curl ...",
)
```

Здесь:

- `BashOperator` — класс оператора;
- `download_data = BashOperator(...)` — экземпляр оператора, который становится task в DAG;
- `task_id="download_data"` — идентификатор task;
- task — конкретная вершина DAG;
- task instance — конкретное выполнение этой task в рамках конкретного DAG Run.

Рабочая формулировка:

Operator — это класс/экземпляр оператора, который описывает единицу работы. Когда operator используется внутри DAG, он становится конкретной task. Task — это элемент DAG, у которого есть `task_id`, зависимости и состояние выполнения.


## 5. Практическое использование

### Пример 1. Последовательный pipeline

Есть процесс:

```
Скачать JSON из API
→ проверить raw-файл
→ преобразовать данные
→ записать витрину
→ отправить уведомление
```

В Airflow это можно представить так:

```
download_data >> check_raw_data >> save_to_storage >> email_end
```

Возможное разбиение:

| task_id | operator_type | Что делает task |
|---|---|---|
| download_data | PythonOperator | Вызывает Python-функцию, которая скачивает JSON с API и сохраняет raw-файл в хранилище |
| check_raw_data | PythonOperator | Проверяет, что raw JSON существует, не пустой и содержит обязательные поля |
| save_to_storage | SparkSubmitOperator | Запускает Spark job: читает raw JSON, преобразует данные и пишет витрину |
| email_end | EmailOperator | Отправляет уведомление об успешной загрузке |

Почему это хорошие границы task:

- ingestion отделён от проверки;
- проверка отделена от transform/load;
- уведомление отделено от записи данных;
- по failed task можно быстро понять, где именно проблема;
- после отладки можно перезапустить только нужную часть.


### Пример 2. Pipeline с параллельными ветками

Есть процесс:

```
download_users
download_orders
download_payments
join_all
build_report
```

Если три загрузки независимы, зависимости можно описать так:

```
[download_users, download_orders, download_payments] >> join_all >> build_report
```

В этом случае:

- `download_users`;
- `download_orders`;
- `download_payments`

можно выполнять параллельно.

Это полезно, потому что ресурсы используются лучше, а общее время выполнения pipeline может стать меньше.


### Пример 3. Ручной DAG без расписания

Если в DAG указано:

```
dag = DAG(
    dag_id="load_currency_rates",
    start_date=...,
    schedule=None,
)
```

то регулярных запусков по расписанию не будет.

Такой DAG можно запускать вручную:

- через UI;
- через API;
- через CLI.

При этом UI всё равно будет показывать:

- статус DAG Run;
- статусы task instances;
- логи;
- ошибки;
- длительность выполнения.


### Пример 4. Rerun после сбоя

Есть DAG:

```
extract >> validate >> load >> notify
```

Если `validate` упала:

- `load` по умолчанию не запустится;
- `notify` по умолчанию не запустится;
- в UI нужно открыть конкретную failed task instance;
- затем посмотреть Logs;
- после исправления причины можно нажать Clear на failed task;
- Airflow сбросит state task instance;
- scheduler заново проверит зависимости и сможет поставить task на выполнение.

Важно:

Clear не делает task “успешной”. Он очищает её состояние, после чего Airflow снова рассматривает task как кандидат на выполнение.


## 6. Подводные камни и диагностика

### 1. Считать DAG обычной цепочкой

Неверно:

```
DAG — это просто задачи одна за другой.
```

Правильно:

```
DAG — это граф зависимостей.
Он может быть линейным, ветвящимся, с fan-out/fan-in, но без циклов.
```


### 2. Думать, что Worker запускает весь DAG-файл

Неверно:

```
Worker запускает скрипт DAG.
```

Правильно:

```
Worker выполняет конкретные task instances, которые scheduler поставил в очередь.
```


### 3. Путать Operator и Task

Рабочее различие:

- Operator — реализация единицы работы;
- Task — конкретный узел DAG;
- Task Instance — конкретный запуск task в рамках DAG Run.


### 4. Проглатывать ошибки

Плохой вариант:

```
try:
    ...
except Exception as e:
    print(e)
```

Если после этого task завершается успешно, Airflow считает её successful, хотя на самом деле результат может быть невалидным.

Правильная логика:

- ошибку можно залогировать;
- но если результат невалиден, task должна упасть;
- Airflow должен увидеть failure state.


### 5. Делать неидемпотентный append

Плохой пример:

```
load_to_dwh каждый раз делает append строк за тот же день.
При rerun появляются дубли.
```

Это небезопасно для rerun.

Лучше:

- overwrite partition за конкретный день;
- delete + insert за период;
- merge/upsert по бизнес-ключу;
- дедупликация перед записью.


### 6. Писать результат только в локальный /tmp

Риски:

- следующая task может выполняться на другом worker и не увидеть файл;
- `/tmp` локален для конкретной машины/контейнера;
- файл может исчезнуть после рестарта контейнера или очистки окружения;
- через какое-то время будет сложно дебажить failed task, потому что исходный файл уже удалён;
- это не долговременное хранилище результата.

Для production лучше использовать:

- S3/MinIO;
- HDFS;
- БД;
- shared storage;
- другое внешнее хранилище.


### 7. Делать тяжёлую обработку внутри PythonOperator

Плохой пример:

```
PythonOperator читает 500 ГБ данных в pandas и обрабатывает их внутри worker.
```

Почему это плохо:

- Airflow worker не должен быть движком обработки данных;
- pandas работает в памяти одного процесса;
- 500 ГБ могут не поместиться в RAM;
- worker будет занят тяжёлой обработкой;
- сложнее масштабировать и диагностировать вычисления.

Лучше:

```
Airflow task запускает Spark job / dbt job / SQL job / контейнер / внешний сервис,
а тяжёлая обработка выполняется в подходящей системе.
```


### 8. Использовать Airflow для streaming workload

Airflow плохо подходит для streaming pipelines.

Причина:

- Airflow рассчитан на batch/recurring tasks;
- у task обычно есть начало и завершение;
- streaming workload постоянно читает поток событий;
- у него нет естественного конца.

Например, постоянно читать Kafka topic и обрабатывать каждое событие с задержкой в секунды — это не основной сценарий Airflow.

Для этого лучше подходят:

- Flink;
- Spark Structured Streaming;
- Kafka Streams;
- другие stream processing tools.

Airflow может участвовать рядом:

- запускать streaming job;
- мониторить внешний процесс;
- запускать batch-догрузку;
- строить ежедневные агрегаты поверх streaming-данных.

Но Airflow не должен быть самим stream processor.


### 9. Использовать Airflow для слишком динамического pipeline

Плохой сценарий:

```
Сегодня DAG создал 5 task.
Завтра 100 task.
Послезавтра 7 task.
Названия и структура task каждый раз сильно меняются.
```

Почему это плохо:

- сложно сравнивать историю запусков;
- непонятно, какая task стала работать дольше;
- UI становится плохо читаемым;
- сложно отлаживать;
- сложно поддерживать код;
- старые task могут исчезать из актуального представления DAG.

Правильная эвристика:

> Один DAG должен соответствовать одному устойчивому workflow/процессу.

**Важно:**
> Это не означает, что любая динамика запрещена: Airflow поддерживает динамическую генерацию DAG и Dynamic Task Mapping.
> Проблема возникает, когда структура workflow нестабильна, плохо предсказуема и перестаёт быть сопоставимой между запусками.


## 7. Сравнения и связанные темы

### Airflow vs cron

Нельзя сказать, что Airflow — это просто “cron с UI”.

| Критерий | cron | Airflow |
|---|---|---|
| Основная идея | Запуск команд по расписанию | Оркестрация workflow/DAG |
| Зависимости между шагами | Нужно реализовывать вручную | Явно задаются в DAG |
| Состояние задач | Сам по себе не хранит как workflow-систему | Хранит DAG Run и Task Instance states |
| UI | Нет встроенного workflow UI | Есть UI для DAG, запусков, статусов и логов |
| Retry | Нужно делать вручную | Можно настраивать на уровне task |
| Rerun отдельного шага | Нужно реализовывать самому | Можно clear/retry отдельную task instance |
| Backfill | Нужно делать вручную | Есть встроенная логика для historical intervals |
| История запусков | Ограниченно/через внешние логи | Есть история DAG runs/task instances |
| Граф задач | Нет | Есть DAG |

Коротко:

```
Cron запускает команды по расписанию.
Airflow управляет DAG-пайплайнами: зависимостями, состояниями, retry, rerun, логами, UI и историей запусков.
```


### Airflow vs data processing engine

| Инструмент | Роль |
|---|---|
| Airflow | Оркестратор |
| Spark | Распределённая обработка данных |
| pandas | Локальная обработка данных в памяти одного процесса |
| dbt | SQL transformation framework |
| Flink / Spark Structured Streaming | Stream processing |
| ClickHouse / DWH | Хранилище / аналитическая БД |

Airflow может запускать Spark/dbt/SQL jobs, но не должен заменять их.


### Task vs Operator vs Task Instance

| Сущность | Что означает |
|---|---|
| Operator | Тип/реализация единицы работы |
| Task | Конкретный узел DAG |
| Task Instance | Конкретное выполнение task в конкретном DAG Run |

Пример:

```
download_data = BashOperator(
    task_id="download_data",
    bash_command="curl ...",
)
```

- `BashOperator` — operator class;
- `download_data = BashOperator(...)` — task в DAG;
- конкретное выполнение `download_data` за конкретный DAG Run — task instance.


### Graph View vs Grid View vs Logs

| UI-раздел | Для чего нужен |
|---|---|
| Graph View | Посмотреть структуру DAG и зависимости между task |
| Grid View | Посмотреть историю запусков и состояния task instances |
| Logs | Посмотреть ошибку конкретной task instance |
| Task details | Провалиться в конкретный запуск task и посмотреть детали |

В старых версиях и книгах вкладка `Grid View` называется `Tree View`.
